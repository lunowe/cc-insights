Know how you really use coding agents.

CC-Insights reconstructs an accurate timeline of agent activity from the logs the agents already write: when you use them, for how long, how often several run at once, which projects take the time, and what it would cost at API list prices. It runs on your machine, stores metadata only, and starts capturing in one command.

§01 The window

Agent logs are a rolling window. A gap in capture is a permanent gap in history.

Claude Code, Codex and opencode each write detailed logs of what they do, and each prunes those logs on a rolling basis. Anything older than the window is deleted by the agent itself. Dashboards can wait. Capture cannot, which is why the first run does everything at once.

1

Config and database

Creates ~/.config/cc-insights, or %APPDATA%\cc-insights on Windows, and the SQLite schema.

2

First ingest

Reads every log the agents still have on disk, incrementally and idempotently.

3

Background job

A launchd job on macOS, a Task Scheduler job on Windows, or one line in your crontab on Linux. Every 15 minutes, or live with --watch.

4

Check-up

cci doctor reports the job, time since the last ingest, and the command that fixes anything wrong. Non-zero exit on real failure.

$ cci install

Watch mode (cci install --watch) follows the logs as they are written, around 0.15 s per cycle. The installer refuses to register both a watcher and a scheduled job, because two writers on one SQLite database is the one way to make it contend with itself. cci install --uninstall removes either and keeps your data.

§03 Honest numbers

Three things that make the numbers trustworthy.

2.4%

Wall-span is not usage.

Sessions sit open for days. On the example corpus, summed session spans come to 2,710 h against 143 h of real activity. Active time is the sum of span durations, where a span breaks on any gap over the idle threshold, and a gap above the threshold contributes zero rather than a capped value.

120–900s

The idle threshold is not a tuning knob.

The measured gap distribution has a wide flat valley between "agent is working" and "user left". Any threshold in that range gives materially the same totals, so the number is backed by measurement rather than chosen to flatter.

1 spec

Every number is reproduced from one reference implementation.

A probe script is the spec for the time math; the derivation engine is tested for exact agreement with it in a single process, because the corpus grows while you measure it. That test exists because three published "measured" numbers turned out to be bugs.

Costs are list-price equivalents, not bills: a subscription charges a flat fee no matter how many tokens run through it. Each API response is counted once, though the logs repeat its usage on every content block, and per-model token totals match ccusage token for token. Rates come from LiteLLM's catalog, committed and keyed by model and date, so a vendor's next price change does not rewrite last month.

§04 Metadata only

Prompt and response text is never stored. Not filtered out. Never written.

The ingest pipeline carries events through a frozen, slots-only dataclass, so an adapter structurally cannot smuggle content through it. That one rule is what makes the multi-machine and team modes safe to run at all.

Stored

  • Timestamps and durations
  • Session, thread and event ids
  • Working directory and git branch
  • Model name
  • Token counts, by component
  • Tool names
  • Source: Claude Code, Codex or opencode

Never stored

  • What you typed
  • What the model answered
  • Tool inputs and outputs
  • File contents
  • Anything a remote service could read without you running cci sync or cci publish yourself

Local SQLite is the source of truth. The dashboard is served read-only on localhost. Nothing leaves the machine unless you sign in and push it.

§05 Machines & teams

Your machines share everything. Your team sees a redacted projection, and nothing else.

These are two different pipes with two different rules, on purpose. sync moves full rows between one person's computers, paths included, because it is all the same person's disk. publish builds what a second person may see, and the projection is computed on your laptop so the shared database physically never receives a path.

Several machines

# device code; approve it in a browser
cci login --server https://your-instance
# send this machine's rows, bring the others' down
cci sync push
cci sync pull
# who has pushed what
cci sync status
  • GitHub device-code sign-in. The token lives in credentials.toml, mode 0600, never in config.
  • Or bring your own PostgreSQL: set CC_INSIGHTS_SYNC_URL and push --direct.
  • Every id is a content hash, so a row that crosses twice collapses instead of duplicating. Interrupted pushes resume.
  • Local SQLite stays the source of truth; the dashboard never changes.

Other people

# what would cross the boundary. Sends nothing.
cci privacy
# asks first, and says what it withholds
cci publish
# you, an admin: mints a join link, shown once
cci team invite
# them: signs in to your server, then redeems
cci team join <link>
  • Published rows are re-keyed on the repo's git remote. No paths, no hostnames, no path-derived ids.
  • The boundary is repo access: if you can see the repo, you can see the agent time on it. Work with no remote stays local, counted rather than silently dropped.
  • Invite links are single-use bearer secrets, stored hashed, valid three days by default. They name your server, so a fresh machine needs nothing else; there is no default server. The redemption is the consent: nobody can be added by id.
  • Joining a team widens nothing on its own: inside a team, only cci team share changes what others can read.

Why not just hash the paths? Because a project id is already sha256(root_path), and a colleague can hash a guess: 555 guesses recovered 20% of the example corpus from the ids alone. So path-derived identity does not cross the boundary at all.

§06 Install

One command on a machine with nothing set up.

The script finds a Python 3.11+ (or names the command that gets you one), installs through pipx when you have it and a managed venv when you do not, links cci into ~/.local/bin, then runs cci install and cci doctor. It never prompts. Re-running it upgrades in place.

With curl

$ curl -fsSL https://raw.githubusercontent.com/lunowe/cc-insights/master/scripts/install.sh | bash

With pipx if you would rather not pipe a script you have not read

$ pipx install cc-insights && cci install

Got a join link from a team admin? Add it, and the script also signs you in and joins the team: … | bash -s -- --join <link>. The link names the server, so nothing else is needed.

Set it up with your coding agent

Paste this into Claude Code, Codex or a similar agent. It installs CC-Insights and walks you through setup, step by step.

If you cannot fetch those files, use this short version:

1. If `cci` is already installed, run `cci doctor`. If it reports `everything is working.`, skip to step 4.
2. Check whether the package is on PyPI: `curl -fsS -o /dev/null https://pypi.org/pypi/cc-insights/json`. On macOS or Linux, if it is on PyPI, run `curl -fsSL https://raw.githubusercontent.com/lunowe/cc-insights/master/scripts/install.sh | bash`. If you get a 404, run `git clone https://github.com/lunowe/cc-insights ~/cc-insights && bash ~/cc-insights/scripts/install.sh`, which also needs pnpm or npm. If I gave you a join link from a team admin (`https://<server>/join/<code>`), add `-s -- --join <link>` to the curl command (or `--join <link>` after `install.sh` in the clone): it also signs me in and joins the team. Treat the link as a password and never echo it. On Windows, run `pipx install cc-insights`, then `cci install`. The installer finds Python 3.11+, installs `cci`, sets up the config, the database and a background job, then runs `cci doctor`. If it needs a Python or a package installed with sudo, give me the command to run.
3. If the installer says its bin directory is not on my PATH, add the line it prints to the shell rc file it names, and tell me which file you edited. On Linux the background job is one line in my crontab; `cci install` writes it and leaves my other entries alone. If it says `no scheduler found`, this machine has no cron: give me the command to install it, then run `cci install` again. Setup is done when `$SHELL -ilc 'cci doctor'` passes.
4. Run `cci stats` and summarize what you see. Active time counts only spans without a gap of more than 5 minutes, so it is far lower than how long sessions sat open. `cci cost` (after `cci price sync`) gives a list-price equivalent, not a bill. Then start `cci serve` in the background so the dashboard opens at http://localhost:8787.
5. Ask me whether I want to sync several machines (`cci login --server <url>`, then `cci sync push` and `cci sync pull`) or share with a team (`cci publish`, `cci team join <link>`, `cci team new`). A join link from a team admin already names the server, and `cci team join <link>` signs in and joins in one step. Otherwise these need an account server URL, which I will give you. There is no public default.

Rules while you do this:
- `cci doctor` decides whether something works. Every line that is not `ok` names the command that fixes it.
- Never delete or move `~/.config/cc-insights` (`%APPDATA%\cc-insights` on Windows), and never change `host_id` in its `config.toml`. The database there holds history the agents have already deleted from their logs. Don't print `credentials.toml`; it holds a token.
- Run exactly one background job per machine. Don't start `cci watch` while a job is installed; use `cci serve` to look at the data.
- Signing in blocks until I approve a code in my browser: `cci login`, `cci team join <link>`, and the installer with `--join` or `--server`. Run it in the background with its output going to a file (for example `nohup cci login --server <url> > /tmp/cci-login.log 2>&1 &`), give me the URL and the code from that file, then check the file every few seconds until it says `signed in as` (or `joined <team>`).
- Before anything leaves this machine for other people, run `cci publish --dry-run`, show me the report, and tell me that anyone on that server with access to those repos on GitHub can read what I publish. Run `cci publish --yes` only after I say yes. If you mint a team join link with `cci team invite`, give it only to me, and tell me it is shown only once and should be sent privately; the person I send it to needs nothing else.

Once everything works, offer to save the skill folder (https://github.com/lunowe/cc-insights/tree/master/skills/cc-insights) into your skills directory, so it is available next time I ask about cci.
